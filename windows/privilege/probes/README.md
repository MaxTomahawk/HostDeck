# B007 intended-client boundary — source-only diagnostic

Owner decision Q-HD-0007, HD-POL-DR01-0007, and HD-REQ-0123–0129. Public source pin: 6c1db056e4f649db29415442de7958501d34f62e. Private canon research pin: e1353f01e48140bcafa12866c99e414b8844137f.

**This is not a signer, authentication decision, approved mandate, deployment or acceptance proof.**

## Verified existing code boundary

Two independently enrolled but same-Windows-SID CurrentUser certificates are used for broker requests. Bridge.Common.ps1 signs request bytes with the user-accessible nonexportable CNG private key. Submit-AdminRequest.ps1 accepts client-provided goal, mandate_evidence, risk, action_summary, project_id and chat_id. Broker.Tick.ps1 receives a queued JSON file and verifies the signature, enrolled client_id, cert, inbox, script hash and limited metadata. It does NOT hold an authenticated IPC connection to the process that initiated signing. Non-critical mandate semantics are client-assessed. A critical goal requires a distinct owner-signed approval. The previously observed unpackaged same-SID ability to use both enrolled keys is an actual negative observation, not merely a hypothesis.

Nonexportable means normal private-key export is prevented; it does not mean a different same-SID process cannot ask CNG to sign. A disabled remote privileged adapter does not prevent the same local Windows user from reaching an authorized public signing helper when ordinary process execution is allowed.

## One-shot metadata probe source

ClientBoundaryProbe.csproj and Program.cs are an **unelevated, read-only and non-installed** .NET 10 Windows probe. It takes two privately selected current process IDs: the candidate Codex process and an existing unpackaged same-SID comparison process. It reads only PROCESS_QUERY_LIMITED_INFORMATION, TOKEN_QUERY and separate READ_CONTROL process handles. It never enumerates other processes or uses signing keys, broker inboxes, privileged APIs, creation/injection rights, process control, network, clipboard or system configuration.

The program reports only categorical JSON about: process and token package identity presence; whether process/token package names agree; TokenIsAppContainer; two observed Windows user SIDs and logon-authentication IDs being equal/unequal; session equality; process creation-time availability; process image location availability; process owner equals observed token user; and whether the process DACL is readable/non-null. **Raw package strings, PIDs, SIDs, logon IDs, paths, parent process records and ACL bytes are not printed.** Image-signature trust, effective DACL rights, parent provenance, package signer, image loaded-module integrity and injection/GUI effects are explicitly NOT_TESTED. Unknown access means UNKNOWN, never positive assurance.

The probe source is deliberately outside the installed broker implementation and its pinned installation manifest. It is NOT built/run by this delegated chat; private Codex review may build using the already approved .NET SDK in an isolated private build directory and invoke with only two authorized observed process IDs. Exit zero means only that both read-only token queries succeeded; it is NOT an intended-client acceptance result. Exit 2 means incomplete observations; 64 means wrong platform/input. Any local IDs or additional diagnostics stay private.

| Metadata | Actual supported observation | Explicitly unsupported conclusion |
|---|---|---|
| MSIX package identity present | Package on this handle/token | App-only protection, exclusive key access |
| AppContainer yes/no | OS token flag | Protected signer or authorization exists |
| Same SID/logon/session | Same kernel-observed account/session metadata at read time | Same intended app or exclusive control |
| Process owner/DACL readable | Current process descriptor is readable | Effective injection resistance, secure parent chain |
| Signed image/publisher/parent/PID | Could be recorded in a separate private trust review | Cryptographic process attestation |

MSIX full-trust medium-IL processes often have package identity but NO AppContainer isolation. ## Specific missing enforcement choice

A protected signer must hold keys **unusable by arbitrary same-SID processes** and independently authorize each concrete action before any privileged effect. The future boundary needs actual authenticated peer IPC (e.g. kernel-observed token/session/package/AppContainer identity), process handle+creation-time tracking, appropriate protected signer/key ACL, true owner/device/goal scope, and denial of unintended peers. A PID, parent, executable path, publisher signature, package Boolean, GUI window or self-declared chat/project field alone cannot be its authorization proof. Process-creation/image observations require a separately trusted source; the existing queued-file broker has no such source. Kernel callbacks are a driver deployment matter, not an authorized probe: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/nf-ntddk-pssetcreateprocessnotifyroutineex .

Two potentially enforceable approaches require a **separate product and deployment decision**:
1. Genuinely isolated Windows logon principals for intended Codex and HostDeck routes with protected key/signing credentials and separate access checks.
2. A separately protected LocalService/SYSTEM signer admitting only validated, isolation-constrained package/AppContainer/capability principals via an authenticated kernel-identity channel, *if actual installed processes support that boundary*, with per-operation owner mandate checks.

A plain shared-SID pipe, accessible user-owned key, signed full-trust MSIX binary or restricted process name is not sufficient. Even a protected signer does not guarantee resistance to same-user injection/GUI control of a legitimately authorized client without independently effective OS isolation. No absolute defence is claimed against a fully compromised Windows user or administrator.

The missing owner choice is precisely which **attacker capability is excluded**, whether an AppContainer/separate-SID client is operationally acceptable, who owns the **separately protected signer/trust root**, and the action/mandate and recovery policy it would enforce. This PR implements none of those transitions and does not self-authorize them.

## Windows readback and bounded package API diagnostics (PR25 follow-up)

Owner's **read-only Windows review** of one current Codex helper (identified by the observed parent chain) against Explorer: process package **ABSENT** for both, token package **UNKNOWN** for both, AppContainer **NO**, same user SID/logon/session **YES**, and process DACL readable. Readable DACL does not prove injection resistance. Three observed Codex.exe helpers had **no WindowsApps image path**; this neither identifies the interactive Codex GUI nor proves the helpers are packaged/MSIX. GUI identity, publisher trust, parent-chain integrity, effective process rights, source application and cryptographic intended-client identity remain **UNPROVEN**.

The native imported API is **GetPackageFullNameFromToken** from Kernel32.dll, with a LONG return code (appmodel.h). Previously the probe mapped all unexpected return codes and exceptions to package_from_token = unknown. The read-only probe now exposes only additional **categorical** fields for process and token calls:

- package_from_token_api_status and package_from_process_api_status: no_package, success, required_length_out_of_bounds, empty_success_value, exception or a not_called_* category when a required handle/metadata operation cannot run. Other failures are labelled length_<category> on the buffer-sizing call or value_<category> on the retrieval call; bounded categories are access_denied, invalid_handle, invalid_parameter, not_supported, insufficient_buffer, no_package, unexpected_success and other_api_error.
- package_from_token_exception_class and package_from_process_exception_class: none or one of a fixed set of standard framework exception class names (including EntryPointNotFoundException, DllNotFoundException, MarshalDirectiveException and SEHException), or OtherException. No exception message, stack, HRESULT, native numeric error code, raw package ID, path or process identifier is published.
- The token package API call now precedes optional WindowsIdentity metadata extraction. An unrelated identity lookup exception cannot prevent or overwrite the package API result. The probe retains exactly PROCESS_QUERY_LIMITED_INFORMATION, TOKEN_QUERY and separate READ_CONTROL; it never signs or uses a privileged service or key.

**Evidence semantics:** a no_package status only records what the OS API reported for that *particular handle/token at that time*. An exception or length_access_denied explains why the token result was UNKNOWN; neither is evidence of ABSENT, a trustworthy package, the GUI, a privileged-client grant or exclusive Codex origin. If the package changes between the buffer and value calls, the result is UNKNOWN. The owner’s previous UNKNOWN remains historical evidence, not retroactively resolved. Microsoft return-code reference: https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagefullnamefromtoken .

## Single smallest protected-signer candidate for the observed unpackaged full-trust clients

**Review proposal, NOT an approved architecture, software implementation or authorization.** The observed third-party Codex helpers and Explorer share the interactive Windows SID. A normal third-party unpackaged/full-trust Codex.exe cannot be uniquely authenticated as the *intended app* by renaming a helper, checking a self-reported PID/parent/image path, applying a generic user-owned ACL, wrapping it in MSIX packaging or reusing the accessible CurrentUser signing keys. We therefore propose protecting each **SYSTEM effect**, not claiming to identify an unmodified Codex process. The separate client-origin requirement remains OPEN.

**Exact proposed architecture:**

1. **One protected signer principal.** In a separately authorized installation, create one small LocalService Windows service with a dedicated service SID. A *new* LocalMachine CNG nonexportable signing key is usable by that service SID and required OS administration only; do not grant the interactive owner SID, Codex helpers or general user applications access. Verify actual KSP support, key-object DACL and effective cross-SID signing denial; the key’s nonexportable flag is not adequate proof. The old broker and its two same-SID CurrentUser enrollments are **not** modified by this source-only PR.
2. **Untrusted proposal-only IPC.** A local-only named pipe with a bounded schema, allowlisted actions, request size, deadline and rate limit may accept proposals from the enrolled user session. Check the peer’s kernel-observed SID/logon/session via an actual authenticated token/impersonation operation, and restore the signer’s identity after inspection. A failure to impersonate or inspect means DENY. **The same SID still does not uniquely identify Codex.** Any such caller is an untrusted proposer; the pipe never exposes keys or a generic sign-arbitrary-bytes function. Deny remote pipe access.
3. **Separately protected owner approval for every elevation.** Bind an explicit owner approval to a canonical digest covering goal, mandate, exact action type and target, script SHA-256, canonical arguments, expected effect, owner/device, risk, UTC expiry and one-time nonce. Verify that signature/approval through an **independent owner key or device channel unavailable to any same-interactive-SID process**; the existing user-accessible owner key or client-declared standard mandate would not suffice. Deny unsigned, unknown, changed, repeated or expired proposals and disconnected/failed approval. Ordinary non-admin actions continue without this new signer.
4. **One signer-to-broker admission route.** Only after the protected approval and allowlist check does the signer sign the canonical action request. A future reviewed broker change admits this protected signer credential for precisely scoped SYSTEM effects, binds the approval digest and rejects unauthorized targets or altered commands **before** execution, retains admission and result receipts and requires real post-effect readback. **At cutover, old same-SID CurrentUser keys must lose direct SYSTEM admission** for this route; otherwise the known bypass remains. Preserve and independently revalidate existing critical owner-approval semantics. The signer does not execute SYSTEM PowerShell itself.
5. **Third-party client truthfulness.** Unmodified Codex can submit a request proposal through an ordinary local helper, but HostDeck cannot enforce that *only* the true vendor Codex app can send it. Any same-SID process could imitate proposals, so the independent exact-effect approval is mandatory. This is **manual, owner-gated elevation**, not unattended privileged Codex autonomy and not cryptographic intended-client authentication. Exclusive unattended app identity would need vendor-supported isolation/attestation or a genuinely separate OS client principal and another owner decision.

**Exact future system effects, all currently UNAUTHORIZED/NOT_RUN:** install the new protected service and local-only pipe, provision its protected machine key, implement external owner approval verification and nonce journal, add an explicit protected-signer enrollment/legacy-key-denial policy to the existing broker, and change the unprivileged request helper to propose rather than self-sign elevated requests. Do not launch a new broker or add a permissive generic PowerShell endpoint. No CURRENT broker task, cert, key, ACL, service, user app or key enrollment changes are part of this PR.

**Review preflight and acceptance:** privately capture current broker version, exact cert/trust list, authorized action inventory, signed binaries, current receipts, user recovery route and protected snapshots without exporting keys. Require an independently protected approval device/key and explicitly reviewed deny-by-default effect allowlist. On a separately approved isolated test installation, require **negative** cross-client signing/admission tests for both formerly usable same-SID keys, arbitrary same-SID proposal and spoofed Codex PID/path, missing/tampered approval, stale nonce, wrong target/script/args and offline signer/approval. Require **positive** one-effect-only authorized transaction with verified target readback, replay denial, durable audit timestamps and preservation of ordinary user work. A valid signature or pipe token alone is never an intended-client PASS.

**Exact rollback/failure posture:** keep the previous binary/config and receipt/journal hashes privately. If signer or approval fails, stop admission of **new elevated effects**, preserve queued/uncertain receipts and use only the separately authorized recovery route. Disable/revoke the *new* signer enrollment and remove its service/key/pipe only after a separate reviewed rollback and evidence retention. **Do not automatically re-enable old same-SID CurrentUser SYSTEM admission**, which would reopen the known flaw; restoring it requires a separate explicit owner risk exception. Non-privileged HostDeck work continues. A backup alone is not rollback evidence.

**Risks:** same-SID processes can still submit requests and exhaust bounded queues; compromised owner approval devices, insecure owner approval UI/GUI automation, approval phishing, broker policy mistakes, forgotten legacy trust, non-atomic cutover, signer availability, key/ACL provider limitations, offline owner, and full Windows user/admin compromise remain. The design needs empirical negative effect tests and does not claim to prevent injection, GUI automation or third-party Codex impersonation merely from process metadata. No AppContainer is inferred from MSIX labelling or an absent WindowsApps path.

**One owner decision to obtain later:** accept or reject this **manual, independently owner-approved per-SYSTEM-effect** model for unmodified unpackaged Codex, including loss of unattended elevation and deny-by-default offline behavior. If unattended elevation or **exclusive Codex origin** is required instead, defer this plan until real vendor/client OS isolation support and a new explicit product decision exist. No consent is implied by this document.
