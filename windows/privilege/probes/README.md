## Verified existing code boundary

Two independently enrolled but same-Windows-SID CurrentUser certificates are used for broker requests. Bridge.Common.ps1 signs request bytes with the user-accessible nonexportable CNG private key. Submit-AdminRequest.ps1 accepts client-provided goal, mandate_evidence, risk, action_summary, project_id and chat_id. Broker.Tick.ps1 receives a queued JSON file and verifies the signature, enrolled client_id, cert, inbox, script hash and limited metadata. It does NOT hold an authenticated IPC connection to the process that initiated signing. Non-critical mandate semantics are client-assessed. A critical goal requires a distinct owner-signed approval. The previously observed unpackaged same-SID ability to use both enrolled keys is an actual negative observation, not merely a hypothesis.

Nonexportable means normal private-key export is prevented; it does not mean a different same-SID process cannot ask CNG to sign. A disabled remote privileged adapter does not prevent the same local Windows user from reaching an authorized public signing helper when ordinary process execution is allowed.

## One-shot metadata probe source

ClientBoundaryProbe.csproj and Program.cs are an **unelevated, read-only and non-installed** .NET 10 Windows probe. It takes two privately selected current process IDs: the candidate Codex process and an existing unpackaged same-SID comparison process. It reads only PROCESS_QUERY_LIMITED_INFORMATION, TOKEN_QUERY and separate READ_CONTROL process handles. It never enumerates other processes or uses signing keys, broker inboxes, privileged APIs, creation/injection rights, process control, network, clipboard or system configuration.

The program reports only categorical JSON about: process and token package identity presence; whether process/token package names agree; TokenIsAppContainer; two observed Windows user SIDs and logon-authentication IDs being equal/unequal; session equality; process creation-time availability; process image location availability; process owner equals observed token user; and whether the process DACL is readable/non-null. **Raw package strings, PIDs, SIDs, logon IDs, paths, parent process records and ACL bytes are not printed.** Image-signature trust, effective DACL rights, parent provenance, package signer, image loaded-module integrity and injection/GUI effects are explicitly NOT_TESTED. Unknown access means UNKNOWN, never positive assurance.

The probe source is deliberately outside the installed broker implementation and its pinned installation manifest. It is NOT built/run by this delegated chat; private Codex review may build using the already approved .NET SDK in an isolated private build directory and invoke with only two authorized observed process IDs. Exit zero means only that both read-only token queries succeeded; it is NOT an intended-client acceptance result. Exit 2 means incomplete observations; 64 means wrong platform/input. Any local IDs or additional diagnostics stay private.

## Specific missing enforcement choice

Protecting privileged effects and proving exclusive **intended Codex-app origin** are **different requirements**. A protected signer must hold signing credentials unavailable to arbitrary same-SID clients. For any proposed SYSTEM effect it must evaluate an explicit authorization policy before signing; **per-effect machine authorization does not require per-effect human permission**.

The owner has already authorized routine HostDeck iterations within the existing goal/scope. A future protected, durable goal mandate and exact deny-by-default effect allowlist may allow repeated **in-scope** actions without asking again on every step. A client-provided goal, mandate_evidence, project_id, chat_id or accessible user-key signature is not an independently protected mandate. The current broker does **not** yet implement the proposed protected policy, and this README does not change any existing authority.

Exclusive vendor Codex origin remains **UNPROVEN**: process name, signed image, PID/parent, Windows package Boolean, same SID/logon/session, full-trust MSIX or user-accessible CurrentUser signing key cannot by themselves exclude another same-SID proposer. Distinct logon principals, genuine package/AppContainer capability isolation or vendor-supported attestation would require separately tested OS/client conditions and a later product decision. No GUI packaging or new user-consent mechanism is assumed.

An independent, manually granted approval for **every** SYSTEM action was a **non-adopted optional design**, not the owner's instruction and not a present HostDeck requirement. It would unnecessarily block already mandated routine automation. Only materially enlarged scope, a new exact effect/target or a reviewed policy exception falls outside the standing mandate; it cannot be self-authorized by a proposal.

## Windows readback and bounded package API diagnostics (PR25 follow-up)

The Codex coordinator's **read-only Windows observation**, not a human approval or independent acceptance, compares one current Codex helper (identified by the observed parent chain) against Explorer: process package **ABSENT** for both, token package **UNKNOWN** for both, AppContainer **NO**, same user SID/logon/session **YES**, and process DACL readable. Readable DACL does not prove injection resistance. Three observed Codex.exe helpers had **no WindowsApps image path**; this neither identifies the interactive Codex GUI nor proves the helpers are packaged/MSIX. The qualified follow-up reports `EntryPointNotFoundException` for the token-package API; this explains UNKNOWN and does not prove token-package absence. GUI identity, publisher trust, parent-chain integrity, effective process rights, source application and cryptographic intended-client identity remain **UNPROVEN**.

The native imported API is **GetPackageFullNameFromToken** from Kernel32.dll, with a LONG return code (appmodel.h). Previously the probe mapped all unexpected return codes and exceptions to package_from_token = unknown. The read-only probe now exposes only additional **categorical** fields for process and token calls:

- package_from_token_api_status and package_from_process_api_status: no_package, success, required_length_out_of_bounds, empty_success_value, exception or a not_called_* category when a required handle/metadata operation cannot run. Other failures are labelled length_<category> on the buffer-sizing call or value_<category> on the retrieval call; bounded categories are access_denied, invalid_handle, invalid_parameter, not_supported, insufficient_buffer, no_package, unexpected_success and other_api_error.
- package_from_token_exception_class and package_from_process_exception_class: none or one of a fixed set of standard framework exception class names (including EntryPointNotFoundException, DllNotFoundException, MarshalDirectiveException and SEHException), or OtherException. No exception message, stack, HRESULT, native numeric error code, raw package ID, path or process identifier is published.
- The token package API call now precedes optional WindowsIdentity metadata extraction. An unrelated identity lookup exception cannot prevent or overwrite the package API result. The probe retains exactly PROCESS_QUERY_LIMITED_INFORMATION, TOKEN_QUERY and separate READ_CONTROL; it never signs or uses a privileged service or key.

**Evidence semantics:** a no_package status only records what the OS API reported for that *particular handle/token at that time*. An exception or length_access_denied explains why the token result was UNKNOWN; neither is evidence of ABSENT, a trustworthy package, the GUI, a privileged-client grant or exclusive Codex origin. If the package changes between the buffer and value calls, the result is UNKNOWN. The owner’s previous UNKNOWN remains historical evidence, not retroactively resolved. Microsoft return-code reference: https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getpackagefullnamefromtoken .

## Smallest reviewable option: protected durable goal mandate and exact effect allowlist

**Design only; NOT implemented, adopted, installed or accepted.** The existing SYSTEM broker, client keys/enrollments, owner-signed critical-action checks, services, ACLs and authorization logic are unchanged. The objective is automatic, bounded **effect authorization** under a faithfully recorded existing owner mandate; it is explicitly **not** a claim to authenticate the third-party Codex process exclusively.

### Trust boundary and smallest components

1. **Protected signer and policy store (future candidate).** Reuse the existing signed broker, with one separate minimal LocalService signer using a dedicated service SID, a service-restricted LocalMachine CNG signing key and durable policy/nonce/audit storage inaccessible for mutation to the interactive user SID. Verify actual KSP/ACL effective access and a negative same-SID key-use test; "nonexportable" alone is insufficient. **No install, key change or enrollment is authorized by this README.** The proposed store must be bound to independently verified provenance of the **owner's existing mandate**, not a copied client-claimed string. Its protected enrollment and revocation are separate reviewed cutover operations; no extra human prompt is necessary for each routine action already inside that protected scope.
2. **Untrusted bounded local proposal.** A same-SID helper may propose through a local-only named pipe with explicit maximum message size, deadline, queue/rate bound and fixed schema: goal/mandate ID, exact effect verb and target, canonical arguments or script SHA-256, required precondition, expected effect, owner/device scope, idempotency key, one-time nonce and request UTC time. Authenticate the peer's OS token/session to enforce local boundary and abuse budgets; failure means DENY. **This does not prove the proposer is Codex.** The pipe cannot expose a key, execute SYSTEM code, alter a mandate or offer generic sign-arbitrary-bytes.
3. **Protected goal mandate, one source of truth.** Versioned protected record: verified owner authority/provenance, mandate_id and goal_id, scope_digest, owner/device binding, allowed client session boundary, effective/expiry UTC, revoke epoch, budget/rate limits, explicit recovery rules and exact permitted effect entries. The owner has already supplied routine scope; that does **not** justify inventing new target permissions, an arbitrary script, unlimited time or unknown goal details. A project ID may be absent without invalidating a real mandate.
4. **Exact deny-by-default effect allowlist.** Begin with **zero** enabled SYSTEM effects. Each separately reviewed record must match *all* of: exact effect verb, canonical target identity, allowed arguments or pinned script SHA-256, risk bound, target precondition, expected postcondition, readback verifier, device/owner/goal, validity, execution limit/rate and rollback category. No wildcards, arbitrary shell/PowerShell, broad directories, unknown targets, changed digest, missing verifiers or implicitly promoted candidate actions. An effect family alone is never a grant.

   **Reviewable policy schema, not an activated permission:**

   | Protected field | Exact condition |
   |---|---|
   | policy_version, mandate_id, goal_id, scope_digest | Real owner mandate provenance; digest does not authenticate who authorized it |
   | owner, device, valid_from_utc, expires_utc, revoke_epoch | Verified binding and finite duration/revocation |
   | effect_allowlist[] | **Initially empty**. Each future entry specifies verb, exact target, constrained arguments/pinned script hash, pre/post state predicates, independent verifier, risk ceiling, max_uses, rate and rollback class |
   | nonce/idempotency journal | Persistent unique request digest and atomic admission state before dispatch |
   | audit_anchor, mandate_provenance | Protected OS/broker evidence separate from the same-SID proposal process |

   **Illustrative format only:** verb windows.service.start + an **exact, separately authorized** target service name + pinned argument/expected readback. With no matching protected effect entry the result is DENY. This README does **not** authorize this service action or nominate a target.
5. **Automatic, per-proposal machine check — not new consent.** On each proposal, validate the protected mandate's current version, scope, exact allowlist entry, canonical digest, target precondition, owner/device, UTC deadline, remaining execution budget and unused nonce. Reserve the authorization atomically **before** sending any effect. Valid in-scope routine actions proceed without asking the owner again. Unknown/changed/expired/revoked effects fail closed and require a substantive scope decision **only if** someone proposes expanding the standing mandate. Preserve existing owner-signed critical-action checks until a separately reviewed replacement demonstrates equivalent or stronger protection.
6. **One signer-to-existing-broker admission path.** Sign only the bounded canonical request, not an arbitrary script or whole uncontrolled command. Before execution the current SYSTEM broker would need a reviewed change to verify policy ID/version, protected signer, nonce, effect and exact target/argument constraints independently. At any later cutover, **old same-SID CurrentUser keys must no longer grant direct SYSTEM admission** for this path; leaving that bypass defeats the proposed boundary. No broker policy, signing, certificate, key ACL, privilege or system effect is changed here.
7. **Independent audit/receipts and recovery.** The existing broker/privileged verifier must record a protected, durable and separately readable transaction: proposal digest, mandate/policy version, signer decision, UTC timestamp, nonce and idempotency ID, broker admission, exact effect target, OS-read target before/after, verifier identity/method and **verified / failed / outcome_uncertain** status. Compare independently observed OS state with the expected effect; client stdout or a valid signature alone is **not** effect proof. Keep raw receipts outside proposer-writable storage, publish sanitized summaries, test audit integrity against same-SID tampering and avoid calling a hash chain immutable against administrator compromise.

   **Crash/timeout/reboot rule:** persist an atomic nonce reservation and budget state before dispatch. Journal states: received -> denied OR reserved -> dispatched -> verified / failed / outcome_uncertain. A lost acknowledgment or uncertain effect **must not be replayed**. Reconcile from broker-owned receipts and actual target readback before any new authorized recovery action. Revocation blocks new effects but does not pretend an already dispatched action was undone.

### Consequences, preflight, negative tests and rollback

- **Autonomy and limits:** the protected standing mandate, once faithfully established, enables repeated authorized routine actions without per-action human approval. The cost is defining the **smallest exact effect/target list** and enforcing it, not a new consent dialogue. There is currently **no adopted allowlist entry** in the probe evidence; none is invented here. Out-of-scope activity is DENIED, not silently added.
- **Read-only preflight before a separately approved cutover:** privately inventory existing mandate authority, broker trust/enrollment and critical-goal gates, intended exact effects/scripts/targets, native signer/key access, current receipts, durable store ownership, state recovery and previous signed version/configuration. Verify that no other same-SID key route can bypass the future protected effect gate. No private IDs, paths, secrets or keys are published/exported.
- **Required negative effect tests in an isolated future installation:** arbitrary same-SID proposer outside scope; fake Codex name/PID/parent; old-key direct SYSTEM route; missing or altered goal/target/script/arguments; wildcard/expired/revoked policy; wrong owner/device; spoofed policy version; missing independent verifier; exhausted rate/count; repeated and concurrent nonces; crash after dispatch/lost receipt; protected journal tampering and signer/key denial. Each must reject new unauthorized effects or preserve uncertainty. **Positive test:** multiple distinct routine iterations under one valid standing mandate, each with exact authorization and independently verified post-effect receipts, **without asking the owner for another approval**. These tests do not assert exclusive Codex identity.
- **Failure, recovery and rollback:** unavailable signer, invalid goal store, uncertain nonce state or failed readback -> DENY **new** SYSTEM requests, preserve pending raw evidence and continue nonprivileged HostDeck work. Roll back the future candidate service/policy/key only under a separately authorized recovery transaction, retaining signed previous versions, config and audit. **Never silently reactivate old same-SID direct SYSTEM admission**, even if that would make a broken integration appear operational. A backup alone is not rollback proof.
- **Residual risks:** any same-SID process can still submit proposals *within* an existing allowed goal, potentially racing or causing an unwanted but allowlisted effect; strict target/state/nonce/budget restrictions mitigate but cannot establish exclusive app identity. Also consider compromised mandate provenance/store, oversized mandates, signer outages, broker confused deputy, non-atomic dispatch, spoofed readback and administrator-level compromise. No unsupported claim of MSIX/AppContainer or GUI identity is made.

**Only remaining product/deployment choice for this candidate (recorded, not asked or answered here):** whether to adopt a protected signer that automatically enforces **the real existing durable owner goal and an explicitly bounded initial effect/target allowlist**, including its trusted enrollment/revocation and recovery route. The exact allowlist members cannot be responsibly filled from this probe and need their own verified source mandate. Mandatory independent manual approval **for every** SYSTEM effect remains a separate **unadopted** option, not an implication of the still-open exclusive Codex-client identity requirement.

## B007 metadata follow-up (source-only; no installed effect)

The optional managed `WindowsIdentity(token)` lookup now has its own categorical `token_identity_status` and `token_identity_exception_class`. If that lookup throws, the independent token AppContainer, session and logon-authentication queries still execute. This corrects an observational coupling only; it does not change process rights, package API binding, signature verification, signer keys, grants or SYSTEM broker behavior. An API `EntryPointNotFoundException` still reports package-from-token UNKNOWN with a fixed exception category; it is never converted to ABSENT or PRESENT. The previous failed token-package observation remains a failed observation.

**Provenance/decision boundary:** the inherited DesktopCommander/RDC file/process helpers supply ordinary user-session execution, not privileged intended-client authentication. The existing HostDeck user-key CNG signing and installed SYSTEM broker already provide enrolled-key verification and SYSTEM execution receipts. They remain the reuse baseline. Neither creates an OS boundary between mutually untrusted same-SID callers; no second broker, PKI or mandate service is introduced by this change. Before choosing any protected signer or policy deployment, separately verify whether the existing broker has a protected policy admission path and exactly which accepted effects it enforces, and obtain the missing concrete owner decision for any new protected effect/target. A design document is not proof of that enforcement.

**Verification limits:** this patch contains no Windows execution or RED/GREEN result; no real process, signature, key, broker or credential test has been run. Independent installed-client acceptance remains open.
