# HostDeck security model and enforcement contract

Status: design accepted after independent review, 2026-10-19; implementation and runtime acceptance pending. Controls in this document are implementation requirements, not claims that they already operate. Baseline: source manifest and engine qualification on main `867a38c87c08ca2963ac93f55d4db67819491f87`. The unavailable v0.1 archive has not been assessed; recovered code must be reconciled against these boundaries before acceptance.

## 1. Assets, actors and limits

Protect the authorized user's desktop, files, application state, credentials, job outputs, device identities, execution receipts and recovery route. Consider malicious clients, injected instructions in documents/websites/tool results, stolen access tokens, compromised adapters, another local Windows user, and accidental misrouting/retries. Treat all model-supplied identity, approval, device and session claims as untrusted input.

Windows kernel, installer trust, protected local configuration and configured authorization server are roots of trust. A local administrator or a process with the same effective user rights as an authorized user executor can inspect or alter that user's work. HostDeck does not claim to isolate mutually hostile processes sharing that security token. OS hardening and separate accounts are required where stronger isolation is needed.

An authorized shell or desktop controller can exercise the target user's broad OS permissions, including by typing into another application. File-path and tool-name allowlists do not sandbox those permissions. This authority must be visible in configuration and consent; scopes cannot be presented as stronger OS isolation than they provide.

## 2. Processes and trust boundaries

| Component | Identity and permitted authority | Must not do |
|---|---|---|
| Windows service and MCP facade | Dedicated restricted service identity, proposed LocalService plus per-service SID; owns protected configuration, journal and local orchestration | Run arbitrary user commands with service privileges or inject desktop input from session 0 |
| Per-user session agent | Unelevated token of the enrolled, logged-in Windows user; bound to SID, logon identity and session ID | Route by display name, use another session by default, cross secure desktop/UAC, or inherit an administrator token silently |
| File/document/terminal engine | Child of the authorized user executor, with explicit workspace/environment and reviewed configuration | Execute the inherited backend as a privileged service, expose its tools directly, or send upstream telemetry |
| Browser adapter | Owned browser profile and local transport under the authorized user; isolated from unrelated personal profiles by default | Accept arbitrary debug endpoints/profile paths supplied by the model or claim DOM control based on desktop clicks alone |
| Update/install broker | Narrow, explicit administrative transaction for exact local product artifacts/ACLs/service registration | Become an unrestricted remote administrator or authorize infrastructure changes |
| External ingress / identity provider | Authenticates clients and forwards through the separately approved transport | Replace resource-server authorization with tunnel possession, forwarding headers or a session ID |
| Operator management adapter | Calls an existing registered bounded action with current authorization and durable receipt | Turn task claims, a model's text or action drafts into shell/root authority |

The proposed service identity must be verified during installation against actual file/network/IPC needs. If it cannot perform a required operation, introduce the smallest explicit broker or user executor; do not silently change the whole service to LocalSystem. A logon bootstrap starts the session agent without making every login task elevated. Administrative installation and external infrastructure publication retain their separate approval procedures.

Windows services cannot safely substitute for an interactive user-session process. The service and user agent communicate over an authenticated local channel. [Microsoft's service guidance](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services) documents this separation.

## 3. Ingress and verified principal

Remote ingress is disabled until OAuth, policy and negative tests pass. Bind development listeners to literal loopback addresses. Check the configured Host and browser Origin on each local HTTP request; no wildcard CORS or cookie-only control endpoint. A reverse proxy is trusted only when its exact connection path is configured; client forwarding headers cannot choose issuer, audience, peer identity or public origin. Streamable HTTP requests are independently authenticated, including subsequent GET/DELETE requests. stdio is a local user launch channel, not a remote authentication substitute.

Use the current MCP HTTP authorization profile, pinned for this design to [MCP 2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). Publish protected-resource metadata and useful 401/403 challenges. The minimal, deployment-approved OAuth metadata needed to authenticate is public; this does not expose protected MCP tool/resource/prompt discovery or private device data. The configured resource identifier is a canonical absolute HTTPS URI, not inferred from incoming headers. Clients request that resource; the server accepts only access tokens intended for it. Never forward the caller's access token to an adapter or another resource server.

The resource verifier creates an immutable principal from verified credentials only: issuer, stable subject, client identifier, granted scopes, expiry and an opaque audit identity. JWT signatures use a maintained verifier and an explicit algorithm/key policy, with an exact configured issuer/audience and finite expiry. Reject ID tokens, unsigned tokens, algorithm confusion, unknown keys and nonfinite time claims. Validate not-before when present with a maximum 30-second clock tolerance. Keys/metadata come from pinned provider configuration with bounded fetch/cache limits, not token-controlled URLs. For opaque tokens, use the configured authenticated introspection endpoint and require an active, resource-bound, finite-lived result. Missing required provider-profile claims fail closed.

Use short-lived access tokens; the deployment profile must configure and verify a maximum ten-minute issued lifetime. No API invents a trusted principal by accepting an `authenticated=true` field. Provider failure cannot activate anonymous access or extend cached credentials beyond their verified expiry. JWT verification does not prove immediate revocation; cache/lifetime limits and server policy revocation are explicit residual controls.

Where HostDeck operates an OAuth client flow, use code+PKCE, state/issuer binding and exact registered redirect URIs. Store refresh tokens only in the designated protected store; rotation or sender constraint belongs to the authorization server/client profile. Bearer tokens remain replayable if stolen until expiry/revocation; TLS, limited lifetime and policy reduce that risk, while supported sender-bound tokens may strengthen it. Operation idempotency does not make a bearer token non-replayable. These constraints follow [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html); provider configuration and ChatGPT interoperability still require actual tests.

## 4. One authorization decision for every public surface

The facade owns a versioned registry of explicit tools, resources and prompts. An adapter cannot add public operations by changing discovery. Each entry names its schema, required scopes, effect class, execution domain and target resolver. Unknown entries or malformed arguments are denied before backend access. Scope names in this design are capability families; the canonical tool catalog will bind each concrete public operation.

Families: `files:read`, `files:write`, `process:execute`, `desktop:observe`, `desktop:control`, `browser:control`, `jobs:read`, `jobs:control`, `artifacts:read`, `devices:read`, and `host:manage`. There is no implicit wildcard or scope hierarchy. Any later hierarchy must be explicit in policy and tests. Tool annotations describe behavior and never grant permission.

Evaluate in this order: verified principal and current expiry; registered operation and schema; required scopes; current server grant for issuer/subject/client and enrolled device; resource ownership and execution identity; session/desktop eligibility when needed; explicit high-impact authorization when required; durable audit admission. Deny/error is final for that attempt. Dispatch only a server-created context bound to that decision. Recheck expiring grants, target identity and effect-sensitive conditions immediately before the effect; reject stale policy/worker generations.

Every grant binds to an enrolled device and allowed execution identity/workspace. No operation falls back to the first online device, active console, administrator account or another browser profile when its target disappears. Selection changes require a new authorized request. Resource and prompt reads, discovery results, jobs, events and image/artifact delivery use the same ownership checks as tool calls. A resource URI cannot bypass a denied tool.

Device enrollment is a separate authority boundary. An authorized local installer/recovery transaction creates a persistent random device ID, nonexportable signing key under the service identity, and enrollment generation in service-protected storage. The authoritative registry binds ID, public-key fingerprint, owner and allowed issuer/client grants to that generation. Hostnames and model-provided IDs are selectors only. The local broker proves its enrolled identity through the protected installation/channel; an ordinary MCP grant or user-executor process cannot enroll a device, edit its key mapping or retarget a grant. Remote enrollment requires an explicitly authorized bounded management transaction showing the actual new key fingerprint; the required action must exist before use.

Remote broker links, when implemented, use mutual TLS against the configured enrollment authority with both peer certificate validation and registered device/key/generation checks; a generic bearer token, tunnel connection or self-asserted worker registration cannot establish a device. No remote worker channel is accepted before this is implemented and tested. This restriction concerns readiness, not a reduction of the required multi-device product scope. Local user agents still use the OS-bound IPC handshake in section 5.

Rotation creates a new protected key/generation through the same authorized transaction, rebinds grants explicitly, and invalidates superseded connections/capabilities. Revocation rejects new calls and closes subscriptions/channels; running effects are cancelled only where safe and otherwise report their actual/uncertain outcome. A reinstall preserves identity only through a verified protected migration; otherwise require fresh enrollment and revoke the old registration before reusing grants. A copied device ID without its key, or an old key/generation restored from backup, is rejected. An administrator copying an actually valid software private key may impersonate that device until revocation; nonexportable keys/hardware binding reduce this risk but do not establish immunity to a compromised host. Enrollment recovery retains the independent administrative route and never silently trusts a clone or reuses display names.

Filesystem-only principals receive confined OS/token and handle-based path enforcement: traversal, alternate path syntax, UNC/device namespaces and reparse-point escapes must be rejected or explicitly allowed under policy. Resolve and validate the object actually opened, not only a string prefix before a race. Shared document formats, embedded URLs and renderers are untrusted and do not receive arbitrary egress or process launch rights. Principals with shell/GUI authority are expressly outside a claim of file-only sandboxing.

Client-supplied job, artifact, session and device identifiers are opaque selectors, not authority. Query results and errors must not reveal another principal's object existence. HTTP sessions and subscriptions are bound to the original issuer/subject/client/device policy context, and are revalidated on reconnect, token expiry, grant changes and adapter generation changes. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) explains session handles, token passthrough and untrusted network-discovery risks; none is replaced by a random identifier alone.

Ordinary authorized operations proceed under the stored grant without a new human prompt each time. Actions outside that grant are denied. Separate administrative, infrastructure and protected-input actions use their existing approval route; neither a tool argument nor a page/document claiming approval changes authority.

## 5. Local IPC and desktop routing

The service/agent handshake binds device, Windows SID, logon identity, session ID, protocol version and agent generation to kernel-observed peer identity. Validate the connected process token/session, not self-reported JSON or a reusable PID alone. The client authenticates the actual broker/channel too. A per-logon protected bootstrap capability/challenge can supplement OS identity; no secret appears in command-line arguments, public config or tool output. Replace capabilities on logoff/restart; reject old generations and reused handshakes.

Named-pipe endpoints reject remote clients. Their explicit DACL permits the service SID and intended logon principal, not Everyone/Users/network accounts. Client access excludes creation of additional server instances; reserve the first instance and fail if the expected endpoint was already created. SID/pipe owner inspection alone is insufficient server authentication. If impersonation is used for identity checks, failure denies execution and the original context is restored in a guaranteed cleanup path; no effect executes as a privileged fallback. [Pipe ACL guidance](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) and [Microsoft's IPC security notes](https://learn.microsoft.com/aspnet/core/grpc/interprocess-namedpipes) inform these requirements.

Check the requested desktop/session immediately before GUI observation or input. Deny session 0, a disconnected/logged-off session, locked or secure desktop, a different SID/logon/session, and elevated targets requiring unavailable rights. Desktop access failure never triggers automatic elevation, credential entry or switching desktops. When an authorized RDP user is the selected target, route to that enrolled session rather than substituting the console. Session changes invalidate cached UIA references, queued input and captured handles.

Use bounded queues, request deadlines and cancellation; isolate hung UIA/provider work so a stuck call cannot block the service. Timeout reports whether an effect is known not to have started, completed or is uncertain. Never retry uncertain input automatically. UI reference/handle records include process creation identity and worker generation to defeat reuse. Captures are sensitive output under owner-scoped ephemeral retention, not routine audit attachments.

## 6. Durable work, evidence and recovery

Journal requests before effects with issuer/subject/client/device/executor identity, operation and argument digest, policy/generation version, idempotency key and state. Idempotency keys are scoped to that complete authority context: same key with changed arguments conflicts, and another principal cannot retrieve a prior result. A client disconnect must not kill accepted jobs. Service/agent restart reconciles journal, PID plus process creation identity and output receipts. Reboot/logoff cannot resurrect an arbitrary shell process; record interruption/uncertainty honestly. Resume only job types with a declared safe checkpoint/idempotency contract, after reauthorization. Never replay arbitrary commands because a completion receipt is missing.

Run user jobs under the designated user executor, with a minimal explicit environment and working directory. Do not inherit service credentials. Job isolation/cancellation must account for child processes and descendants. Large output becomes an owner-scoped artifact with size/quota limits, content hash, expiry and authenticated retrieval. Download/preview URLs must be capability-bound and short-lived if used; bearer credentials never appear in URLs. Canonical paths and ownership are checked on each retrieval/deletion. Event subscriptions filter by the same identity, stop at expiry/revocation and do not publish secret argument or output bodies.

The durable audit records safe operation identifiers, pseudonymous actor/device IDs, decisions/reason codes, policy version and effect/receipt linkage. No raw tokens, arguments, file contents, environment, clipboard, screenshots or command output belong in routine logs. Sensitive argument correlation uses a keyed digest over canonical bytes with a separate protected audit key; low-entropy secrets must not become guessable unkeyed hashes. Chain records to detect local corruption; do not claim this defeats an administrator who controls the host/key. Protected external checkpoints may provide a separate anchor only through an approved export path.

Audit/journal admission failure denies new effects. If storage fails after an effect starts, mark uncertainty using the independent available receipt channel and stop further effects; do not claim rollback or exactly-once execution. Disk exhaustion, log rotation, quotas and recovery require injected-failure tests.

Recovery control uses a separately authenticated local CLI/SSH route and a bounded privileged broker when necessary. Stopping MCP must not disable that route. Updates stage exact hashed/signed artifacts from reviewed main, verify identity/compatibility/health, atomically select a version and preserve a tested rollback. Reject untrusted paths, changed hashes, downgrade outside the approved rollback transaction and unreviewed script hooks. No tunnel/DNS/firewall/identity changes or scheduled monitoring are authorized merely by this design.

## 7. Acceptance evidence and remaining risk

`SECURITY_ACCEPTANCE.md` assigns negative/positive scenarios to implementation boundaries. A design review accepts this contract only. Runtime policy, OAuth, Windows IPC, session and recovery tasks must supply real evidence and independent review before their completion. Tests using fabricated principals or providers can exercise decision logic but cannot establish token verification, Windows ACLs or ChatGPT interoperability.

Known release risks remain: inherited credential candidates in public history; unavailable prototype source; upstream loose risk classification/in-memory audit/protocol echo; unqualified alternative engine runtimes; unproven service/session lifecycle, rich clipboard/browser behavior, current protocol, remote identities, installer and rollback. None is waived by engine qualification. Reconcile this model when a source module adds a capability, dependency, authority domain or external connection.
