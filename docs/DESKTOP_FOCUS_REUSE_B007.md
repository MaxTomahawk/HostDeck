## Existing functions and exact call gap

- **Pinned Windows Commander:** `exalsch/windows-commander-mcp@a5b33fed0994dc65782bf8cfb8e1168253098fcf`, `src/WindowsCommander.Windows/Services/WindowService.cs`. The vendored `windows/vendor/WindowsCommander.Windows/Services/WindowService.cs` is **byte/line-identical** (same Git blob `75a78b323ad32626a4a0d43e1ad102a8a4f0c0d8`). `WindowService.FocusWindow` calls `ForceForeground`, which attempts `SetForegroundWindow`, thread-input attachment, and a bounded retry, then validates `GetForegroundWindow()==target HWND`. Its already-existing fallback also temporarily writes/restores `SPI_SETFOREGROUNDLOCKTIMEOUT`; this source review does **not** execute, extend, or endorse global foreground-setting changes.
- **Existing UIA:** vendored `windows/vendor/WindowsCommander.Windows/Services/UiAutomationService.cs`, `InvokeUiElement(elementRef,"focus")` calls `AutomationElement.SetFocus()` and reports completion when that call returns without an exception. `SetUiValue` instead uses `ValuePattern.SetValue`. Neither operation proves the top-level foreground HWND. Microsoft explicitly documents that `AutomationElement.SetFocus` **does not necessarily bring the element to the foreground or make it visible**. UIA keyboard focus and verified global foreground are not interchangeable.
- **HostDeck adapter:** `windows/HostDeck.DesktopWorker/Program.cs`: `Dispatch("hostdeck_window_action", kind="focus")` uses the existing `windows.FocusWindow`, not UIA; `hostdeck_invoke_ui_element` separately exposes existing UIA focus after `ResolveElement`. `hostdeck_type_text`, `hostdeck_send_keys`, and `Mouse` go through `FocusAndVerify`, which also compares the actual foreground HWND and fails closed with `WINDOW_NOT_FOREGROUND`. `ResolveWindowId` checks freshness, HWND/PID/process start and session. The UI tree refresh invalidates element references; the unchanged owner/session/reauthorization boundary sits in `src/hostdeck/desktop.ts`. Do not bypass these checks.
- **Thread premise:** HostDeck `Program.Main` is marked `[STAThread]` but uses `async Task Main` and `ReadLineAsync`; pinned Windows Commander `src/WindowsCommander.McpServer/Program.cs` also uses asynchronous stdio. Neither source proves a specific thread/apartment diagnosis at the actual focus call. No new STA loop or worker follows from this comparison.
- **Pinned CursorTouch reference:** `CursorTouch/Windows-MCP@128f2960c79b74bd2630f4dbc9d4f664f4ce89b3`, `src/windows_mcp/desktop/service.py`: `Desktop.switch_app` calls `bring_window_to_top`, then waits up to one second for `win32gui.GetForegroundWindow()==target`. `bring_window_to_top` reuses Win32 foreground/attachment operations, but calls `AllowSetForegroundWindow(-1)` (all processes), which is **not an authorized HostDeck adapter fix**. `tests/test_app_switch_foreground.py` mocks the foreground result; these are contract tests, not demonstrated activation of HostDeck's own WinForms fixture. Its `uia/controls.py` `SetFocus` also lacks top-level foreground proof.
