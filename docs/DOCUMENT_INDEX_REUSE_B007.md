## Windows Search — first narrow query qualification, without provider adoption

1. **Identity and read boundary.** A trusted local Windows worker (not the remote relay) would issue a read-only `SELECT` against `SystemIndex` using the intended user/executor identity. Service identity and Windows index crawl identity differ; a service process is not proof of a user's effective query authorization. Existing HostDeck PolicyGate and corpus-root checks are mandatory. Do not create a COM service, enable a service, register an IFilter, expand Windows crawl roots or reindex.
2. **Query semantics and result shape.** Translate a bounded, explicitly typed HostDeck content query to Windows Search SQL/AQS (for example `CONTAINS`/`FREETEXT`, chosen `SCOPE`/`DIRECTORY`, capped `TOP` and `ORDER BY System.Search.Rank DESC`); escape identifiers/literals and reject unsupported query modes. `System.Search.Rank` is provider-specific, **not FTS5 BM25**; expose provider + rank semantics and deterministic path tie-break, never compare scores across engines. No claim that regexp, arbitrary substring, implicit stemming or all file types are equivalent.
3. **Authorization before disclosure.** First fetch bounded **internal candidate paths/IDs**; canonicalize without following unapproved reparse/junction targets; verify selected scope, device/executor/client PolicyGate, live Windows file/ancestor read rights with the actual requester token, and current source existence. Only then fetch/open any displayed metadata, body-derived snippet, or filename. Compute **visible counts solely from authorized candidates**; do not return a raw `SystemIndex` count, inaccessible candidate rank, a leak via truncated/empty-state, or raw provider exception. Check again at readback and treat races as a denied/partial result, not an implicit grant.
4. **Paging, time, freshness.** Use a bounded OLE DB rowset or bounded query window with strict deadline, result/byte cap and cancellation of the **owned query**. If internally collecting candidate windows for ACL post-filtering, cap candidates and report partial/unknown total rather than returning unauthorized counts. Windows Search's mutable asynchronous index is **not** a frozen snapshot: offset pagination may drift; use a sealed authorized response page set or provider-specific cursor semantics with visible drift status, no promise of stable whole-corpus paging. Verify search API index-readiness, actual indexed locations, `System.Search.Contents`/IFilter functionality, language and missing/metadata-only types separately. Source-file freshness is not proven by an index hit.
5. **Lifecycle/resources and privacy.** Windows Search owns its existing crawl/maintenance/stop/recovery. HostDeck may stop an **owned query**, not pause/resume the OS index service on the user's behalf. No new HostDeck persisted extracted-text database is needed for the query route; the **pre-existing OS index already stores metadata/content** under Windows policy. Measure query CPU/RAM/I/O/latency and returned bytes on selected **owned fixtures** before a performance claim. A running WSearch service is only a provider-present observation.

**Smallest consistent HostDeck diff if later selected:** new optional read-only `windows.search.systemindex.v1` provider implementing the existing typed full-text query/result/coverage interface, wired through the same PolicyGate + native worker identity and bounded search-job/page/cancel conventions. Register it as an **explicit alternative**, not the implicit default for `search_files`, not an extension of Everything's name provider, and not an authorization bypass. Unsupported controls (OS-index pause, build, resume, repair, indexing) must remain **unsupported**, not stub-success. The actual worker COM/OLE DB ABI, architecture and session behavior require the owner's later Codex-led Windows qualification before code adoption.

## Scope and decision boundary

- Full HostDeck scope means **any explicitly selected and authorized eligible locations/volumes and formats that can pass provider/ACL checks**. A historical three-volume preview is neither the whole target corpus nor a general three-user-folder maximum. Fixed-volume roots, protected exclusions, reparse checks and effective rights do not relax silently. No implicit UNC/network, external media, cloud or cross-user discovery.
- Resource profiles are **proposals bound to the measured device hardware and observed corpus size**, with explicit CPU/RAM/free-disk/IO, candidates/pages, concurrency and freshness/update budgets. No hardcoded CPU/RAM thresholds or sweeping 'index everything' activation follows from available memory. Exact dataflow, extracted-content retention, index owner/ACL and resource effect remain reviewable before owner selection.
- **Review-only recommendation:** qualify the already-running Windows Search `SystemIndex` API/IFilter and effective ACL coverage **first** using a distinct disposable corpus and read-only query if independently authorized; compare Recoll's isolated query API for material missing document types/coverage, DocFetcher's GUI bridge only if GUI dependence and exposure can be accepted, and Tika solely as an extraction supplement. Keep existing FTS5 dormant. **This is not an engine choice, a corpus choice, a deployment plan or an owner approval.**
